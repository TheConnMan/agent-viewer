# Codex `app-server` as the agent-viewer Codex backend

Research note. Investigated 2026-07-26 against codex-cli **0.144.4** on this box.
Every claim below carries either a schema file path plus the quoted JSON fragment, or exact
captured command output. Speculation is labelled.

Schema source of truth used throughout:
`/home/example/.claude/jobs/0214d552/tmp/cxschema/` (generated by
`codex app-server generate-json-schema --out <DIR>`), which contains 37 unversioned files, a
`v1/` dir (2 files: `InitializeParams.json`, `InitializeResponse.json`) and a `v2/` dir
(228 files) holding the thread/turn API.

## 1. Connection strategy

### Verdict: connect directly to the Unix control socket and speak **WebSocket-framed JSON-RPC**. Do not use `codex app-server proxy`.

The control socket is **not** a raw JSONL endpoint. It is an HTTP/WebSocket listener over
`AF_UNIX`. Discovered by stracing the one command that is known to work against it,
`codex app-server daemon version`:

```
132691 sendto(10, "GET / HTTP/1.1\r\nHost: localhost\r\nConnection: Upgrade\r\nUpgrade: websocket\r\nSec-WebSocket-Version: 13\r\nSec-WebSocket-Key: j5Bq+g1zXbeqG2fXX4AcFw==\r\n\r\n", 148, MSG_NOSIGNAL, NULL, 0) = 148
132691 recvfrom(10, "HTTP/1.1 101 Switching Protocols\r\nconnection: Upgrade\r\nupgrade: websocket\r\nsec-websocket-accept: CoMacLdzwmXvsP0/3SEL1KR2Cb4=\r\n\r\n", 4096, 0, NULL, NULL) = 129
132691 sendto(10, "\201\376\0\217C\343~\235...", 151, MSG_NOSIGNAL, NULL, 0) = 151
132691 recvfrom(10, "\201~\0\310{\"id\":1,\"result\":{\"userAgent\":\"Codex Desktop/0.144.4 ...", 131072, 0, NULL, NULL) = 420
```

(masked client frames, opcode `0x81` = text; this is RFC6455.)

**`codex app-server proxy` is broken against this socket in 0.144.4.** Its help text says
"Proxy stdio bytes to the running app-server control socket", and strace confirms it does a
literal byte relay with no WebSocket upgrade, so the daemon immediately EOFs the connection:

```
132095 socket(AF_UNIX, SOCK_STREAM|SOCK_CLOEXEC|SOCK_NONBLOCK, 0) = 10
132095 connect(10, {sa_family=AF_UNIX, sun_path="/home/example/.codex/app-server-control/app-server-control.sock"}, 69) = 0
132095 sendto(10, "{\"id\": 1, \"method\": \"initialize\", \"params\": {\"clientInfo\": {\"name\": \"probe\", \"version\": \"0.0.1\"}}}\n", 99, MSG_NOSIGNAL, NULL, 0) = 99
132095 recvfrom(10, "", 8192, 0, NULL, NULL) = 0
```

A direct raw-JSONL socket connect from Python behaves identically (`recv 0 bytes` / `EOF`).
Both paths were tried before the WebSocket discovery; both fail.

### Socket discovery

Do not hardcode the path. `codex app-server daemon version` is a read-only status probe that
prints it:

```
$ codex app-server daemon version
{"status":"running","managedCodexPath":"/home/example/.codex/packages/standalone/current/codex","managedCodexVersion":"0.144.4","socketPath":"/home/example/.codex/app-server-control/app-server-control.sock","cliVersion":"0.144.4","appServerVersion":"0.144.4"}
```

`socketPath` is the field to use. `status: "running"` is the availability gate; if it is not
running, agent-viewer should fall back rather than start a daemon (starting one is a
user-visible side effect).

### The handshake

`v1/InitializeParams.json`:

```json
  "required": [
    "clientInfo"
  ],
  "properties": {
    "capabilities": { "anyOf": [ { "$ref": "#/definitions/InitializeCapabilities" }, { "type": "null" } ] },
    "clientInfo": { "$ref": "#/definitions/ClientInfo" }
  }
```

`ClientInfo` requires `name` and `version` (optional `title`). `InitializeCapabilities` is
where the interesting knobs are:

```json
        "experimentalApi": {
          "description": "Opt into receiving experimental API methods and fields.",
          "default": false, "type": "boolean"
        },
        "optOutNotificationMethods": {
          "description": "Exact notification method names that should be suppressed for this connection (for example `thread/started`).",
          "type": ["array","null"], "items": { "type": "string" }
        },
```

`optOutNotificationMethods` is directly useful: agent-viewer can suppress the high-volume
delta notifications (`item/agentMessage/delta`, `item/reasoning/textDelta`,
`item/commandExecution/outputDelta`) it does not render.

Envelope is bare JSON-RPC-ish, **no `"jsonrpc": "2.0"` field**. `ClientRequest.json` requires
exactly `id`, `method`, `params`; `ClientNotification.json` defines a single client
notification, `initialized` (no params). Sequence: `initialize` request, read the response,
then send the `initialized` notification.

**Auth: none on the local Unix socket.** The `--ws-auth`, `--ws-token-file`,
`--ws-shared-secret-file` options in `codex app-server --help` are documented as "Websocket
auth mode for **non-loopback** listeners". No token was sent in the working `daemon version`
strace, and an unauthenticated connect from an arbitrary process succeeded (see live output
below). Anything that can read the socket file has full control of the user's Codex.

### Live proof the handshake works from a third-party process

Raw output of a hand-rolled WebSocket client (`/tmp/cxws.py`, Python stdlib only):

```
HTTP: HTTP/1.1 101 Switching Protocols
<< {"id":1,"result":{"userAgent":"Codex Desktop/0.144.4 (Ubuntu 24.4.0; x86_64) unknown (agent-viewer-probe; 0.0.1)","codexHome":"/home/example/.codex","platformFamily":"unix","platformOs":"linux"}}
<< {"method":"remoteControl/status/changed","params":{"status":"connected","serverName":"remote-dev","installationId":"17706cfc-bf7e-4732-9a28-fc47045a2799","environmentId":"env_e_6a3516b50cec8330afa7b827c187467f"}}
```

Note the `userAgent` echoes our `clientInfo` (`(agent-viewer-probe; 0.0.1)`) into the daemon's
own UA string, and the daemon self-identifies as **Codex Desktop** because Codex Desktop is
what started it.

### Rejected alternative: private `codex app-server` per TUI launch

`codex app-server --stdio` spawned privately would work and would avoid the WebSocket layer
(stdio transport is plain JSONL). Rejected because a second app-server process would not see
the threads the user's real daemon has loaded, so `thread/loaded/list` and every live status
would be empty for exactly the sessions the user cares about, and it doubles the model/auth
process footprint. Use it only as a fallback when `daemon version` reports not-running.

## 2. Enumeration: `thread/list`

### Request

`v2/ThreadListParams.json` (all fields optional):

```json
    "sourceKinds": {
      "description": "Optional source filter; when set, only sessions from these source kinds are returned. When omitted or empty, defaults to interactive sources.",
      "type": ["array","null"], "items": { "$ref": "#/definitions/ThreadSourceKind" }
    },
    "archived": {
      "description": "Optional archived filter; when set to true, only archived threads are returned. If false or null, only non-archived threads are returned.",
      "type": ["boolean","null"]
    },
    "cursor": { "description": "Opaque pagination cursor returned by a previous call.", ... },
    "cwd": {
      "description": "Optional cwd filter or filters; when set, only threads whose session cwd exactly matches one of these paths are returned.",
      ...
    },
    "limit": { "description": "Optional page size; defaults to a reasonable server-side value.", ... },
    "useStateDbOnly": {
      "description": "If true, return from the state DB without scanning JSONL rollouts to repair thread metadata. Omitted or false preserves scan-and-repair behavior.",
      "type": "boolean"
    },
    "searchTerm": { "description": "Optional substring filter for the extracted thread title.", ... },
    "sortDirection": { ... },   // "asc" | "desc", default desc
    "sortKey": { ... }          // "created_at" | "updated_at" | "recency_at", default created_at
```

`ThreadSourceKind` enum:

```json
    "ThreadSourceKind": {
      "type": "string",
      "enum": ["cli","vscode","exec","appServer","subAgent","subAgentReview","subAgentCompact","subAgentThreadSpawn","subAgentOther","unknown"]
    }
```

So yes: paging, archived filter, cwd filter, title search, sort, **and a server-side
source-kind filter that excludes subagents**.

`useStateDbOnly: true` is the fast path and is what agent-viewer wants for its 1-2s refresh
loop; the default does a JSONL rollout scan to repair metadata, which over 4,194 threads is
not something to do on a timer.

### Response

`v2/ThreadListResponse.json` top level:

```json
  "required": ["data"],
  "properties": {
    "backwardsCursor": { ... },
    "data": { "type": "array", "items": { "$ref": "#/definitions/Thread" } },
    "nextCursor": {
      "description": "Opaque cursor to pass to the next call to continue after the last item. if None, there are no more items to return.",
      "type": ["string","null"]
    }
  }
```

`Thread` required fields: `cliVersion, createdAt, cwd, ephemeral, id, modelProvider, preview,
sessionId, source, status, turns, updatedAt`. Optional/notable:

- `name` — "Optional user-facing thread title."
- `preview` — "Usually the first user message in the thread, if available." (the summary line)
- `gitInfo` — `{ branch, originUrl, sha }`, all nullable
- `cwd`, `createdAt`, `updatedAt`, `recencyAt` (unix seconds)
- `source` (`SessionSource`) and `parentThreadId` — "This will only be set if this thread is a subagent"
- `agentNickname` / `agentRole` — sub-agent labels
- `path` — "[UNSTABLE] Path to the thread on disk." (the rollout JSONL)
- `turns` — "Only populated on `thread/resume`, `thread/rollback`, `thread/fork`, and `thread/read` (when `includeTurns` is true) ... For all other responses ... the turns field will be an empty list."

`SessionSource` is the serialized enum agent-viewer already handles, and the schema confirms
the defensive parse the repo's CLAUDE.md mandates:

```json
    "SessionSource": {
      "oneOf": [
        { "type": "string", "enum": ["cli","vscode","exec","appServer","unknown"] },
        { "type": "object", "required": ["custom"], "properties": { "custom": { "type": "string" } }, "title": "CustomSessionSource" },
        { "type": "object", "required": ["subAgent"], "properties": { "subAgent": { "$ref": "#/definitions/SubAgentSource" } }, "title": "SubAgentSessionSource" }
      ]
    }
```

`ThreadStatus` is a tagged union of exactly four shapes:

```json
"NotLoadedThreadStatus" -> {"type":"notLoaded"}
"IdleThreadStatus"      -> {"type":"idle"}
"SystemErrorThreadStatus" -> {"type":"systemError"}
"ActiveThreadStatus"    -> {"type":"active","activeFlags":[...]}   // ThreadActiveFlag: "waitingOnApproval" | "waitingOnUserInput"
```

### Subagent exclusion is server-side and works

Live histogram over one page, same daemon, two calls:

```
DEFAULT sourceKinds -> n= 11  source histogram: Counter({'"vscode"': 11})
ALL sourceKinds -> n= 100  source histogram: Counter({'"exec"': 48, '{"subAgent": "review"}': 42, '"vscode"': 4, '{"subAgent": {"thread_spawn": {"parent_thread_id": "019f984c': 3, '{"subAgent": {"other": "guardian"}}': 3})
sample subagent rows: [('019f9ac7', {'subAgent': 'review'}, None, None), ...]
```

Two things follow:

1. Subagent/companion threads are excluded by the **default** `sourceKinds`, without reading
   SQLite. The 694-of-1,279 subagent problem is solved by the server.
2. The default also excludes `exec` (48 rows in that window were `exec` and none appeared in
   the default page). agent-viewer must pass an explicit
   `sourceKinds: ["cli","vscode","exec","appServer"]` to match today's behavior.

### Paging gotcha (real, observed)

The default call returned **11 rows for `limit: 200`** and still handed back a `nextCursor`.
The server appears to page the underlying store first and filter by source afterwards, so a
page can be arbitrarily short while more data exists. **Never treat a short page as the end of
the list — loop until `nextCursor` is null.**

### Verdict: `thread/list` alone can drive the list. SQLite is no longer needed for enumeration.

Title, preview, cwd, git branch/origin, timestamps, archived filter, subagent exclusion, and
paging are all covered. SQLite would only still be needed for (a) live status of sessions the
daemon does not host (see section 4) and (b) any field this project reads that is not in
`Thread` — none identified.

## 3. Live state / notifications

**There is no `thread/subscribe` method.** Full method list extracted from
`ClientRequest.json` (`jq -r '.oneOf[].properties.method.enum[0]'`) contains
`thread/unsubscribe` but no subscribe counterpart. The subscribing actions are
`thread/start`, `thread/resume`, and `thread/read` — i.e. loading a thread subscribes the
connection to it, and `thread/unsubscribe` releases it. `ThreadUnsubscribeResponse` confirms
the state machine:

```json
    "ThreadUnsubscribeStatus": { "type": "string", "enum": ["notLoaded","notSubscribed","unsubscribed"] }
```

Connection-scoped notifications start flowing immediately after `initialize`, with no
subscription at all — proven live, the daemon pushed an unsolicited notification one frame
after the initialize result:

```
<< {"method":"remoteControl/status/changed","params":{"status":"connected","serverName":"remote-dev",...}}
```

Relevant server notifications (from `ServerNotification.json`): `thread/started`,
`thread/status/changed`, `thread/closed`, `thread/archived`, `thread/unarchived`,
`thread/deleted`, `thread/name/updated`, `thread/compacted`, `thread/tokenUsage/updated`,
`turn/started`, `turn/completed`, `turn/diff/updated`, `turn/plan/updated`, `item/started`,
`item/completed`, plus the delta firehose (`item/agentMessage/delta`,
`item/reasoning/textDelta`, `item/commandExecution/outputDelta`, ...).

`ThreadStatusChangedNotification` carries exactly `{threadId, status}` with the same four-way
`ThreadStatus` union as the list response, so the same decoder serves both.

### Verdict: ACHIEVABLE — with one unresolved scope question.

Mechanically this is clean: one long-lived connection, notifications arrive unsolicited, and
`optOutNotificationMethods` lets us mute the deltas. The unresolved part is **which** threads
a merely-initialized connection gets `thread/status/changed` for: all threads the daemon
hosts, or only threads this connection has subscribed to via `resume`/`read`. I could not test
this — `thread/loaded/list` returned `{"data":[],"nextCursor":null}` during the whole window,
so no thread was live to emit a transition.

*Speculation (labelled):* given `thread/unsubscribe` returns `notSubscribed` as a distinct
state, subscription is almost certainly per-connection and per-thread, and lifecycle
notifications (`thread/started`, `thread/archived`) are probably global while item/turn deltas
are probably subscription-scoped. This must be verified against a live turn before it is
designed around.

## 4. Attach: the critical question

### The promising evidence

`v2/ThreadResumeParams.json` description, verbatim:

```
"There are three ways to resume a thread: 1. By thread_id: load the thread from disk by thread_id and resume it. 2. By history: instantiate the thread from memory and resume it. 3. By path: load the thread from disk by path and resume it.\n\nFor non-running threads, the precedence is: history > non-empty path > thread_id. If using history or a non-empty path for a non-running thread, the thread_id param will be ignored.\n\nIf thread_id identifies a running thread, app-server rejoins that thread and treats a non-empty path as a consistency check against the active rollout path. Preferusing thread_id whenever possible."
```

**"If thread_id identifies a running thread, app-server rejoins that thread"** is the exact
no-duplicate-session semantics the project requires. Paired with:

- `turn/steer` — `{threadId, expectedTurnId, input}`, where `expectedTurnId` is a
  "Required active turn id precondition. The request fails when it does not match the
  currently active turn." That is inject-input-into-a-live-turn.
- `turn/interrupt`, `thread/inject_items`, and the `item/*/delta` notification stream, which
  together are a full read-and-write attach surface.
- `command/exec`, `command/exec/write`, `command/exec/resize`, `command/exec/terminate` for
  terminal interaction.

### The blocker

"Running" means **running inside this app-server process**. `thread/loaded/list` is documented
as "Thread ids for sessions currently loaded in memory", and live it returned empty:

```
loaded/list: {"id":10,"result":{"data":[],"nextCursor":null}}
```

Correspondingly, **every one of the 100 threads sampled reported `notLoaded`**:

```
status histogram (all): Counter({'{"type": "notLoaded"}': 100})
```

A `codex` TUI the user launched in their own terminal, or a `codex exec` fired by a background
job, is a **separate OS process** with its own in-memory session. The daemon does not host it,
so it will be `notLoaded` and `thread/resume` on it would load a *second* copy from the
rollout file — exactly the duplicate-session failure the project forbids. agent-viewer's
current `/proc/fd` PID-to-`rollout_path` correlation detects those processes; the app-server
structurally cannot.

I could not empirically confirm this, because no external `codex` session was running during
the investigation window (`pgrep -af codex` showed only the daemon,
`codex -c features.code_mode_host=true app-server --listen unix://`, PID 23921, PPID 1).
**Labelled as strong inference, not verified.**

### Verdict: ACHIEVABLE-BUT-FRAGILE, split by session origin.

- For threads the daemon hosts (Codex Desktop / VS Code / anything launched through
  app-server): **ACHIEVABLE**. `thread/resume` rejoins in place, `turn/steer` injects,
  `item/*` deltas render, no duplicate session, no PTY.
- For threads owned by an external `codex` process: **NOT-PRACTICAL** via app-server. Those
  still need today's PTY path (`codex resume <id>` exec'd into the terminal) plus the
  `/proc/fd` status correlation.

A migration that drops SQLite and the PID correlation wholesale would regress live status and
attach for exactly the CLI-launched sessions this tool exists to watch. The safe shape is
app-server for enumeration/mutations/rich state, retaining process correlation for
externally-owned sessions.

## 5. Mutations

All confirmed present in `ClientRequest.json`. **Not executed** — read-only investigation, per
constraints. Exact calls that would be made:

| Action | Method | Params | Schema |
|---|---|---|---|
| Rename | `thread/name/set` | `{"threadId": "<uuid>", "name": "<new name>"}` | `v2/ThreadSetNameParams.json` (`required: ["name","threadId"]`) |
| Archive | `thread/archive` | `{"threadId": "<uuid>"}` | `v2/ThreadArchiveParams.json` |
| Unarchive | `thread/unarchive` | `{"threadId": "<uuid>"}` | `v2/ThreadUnarchiveParams.json` |
| Delete | `thread/delete` | `{"threadId": "<uuid>"}` | `v2/ThreadDeleteParams.json` |
| Stop | `turn/interrupt` | `{"threadId": ...}` | `v2/TurnInterruptParams.json` |

**`thread/name/set` is a genuine rename, and the evidence is strong.** Three independent
signals:

1. `Thread.name` is described as "Optional user-facing thread title." — a real persisted
   field, distinct from `preview` ("Usually the first user message in the thread").
2. The live list response shows real persisted names on threads that were never named by the
   Codex TUI: `"name":"Codex Companion Task: say hi"` where `"preview":"say hi"` — the name
   and the first message are different strings, so `name` is stored independently and is not a
   derived title.
3. There is a dedicated broadcast notification, `thread/name/updated`
   (`v2/ThreadNameUpdatedNotification.json`), so the rename propagates to every connected
   client. That is not the shape of a cosmetic no-op.

`ThreadSetNameResponse` is `{"type": "object"}` with no required fields — an empty ack, so
success must be confirmed via the absence of a JSON-RPC error and/or the
`thread/name/updated` notification, not via a response body.

`thread/archive` / `thread/unarchive` / `thread/delete` each have a matching notification
(`thread/archived`, `thread/unarchived`, `thread/deleted`), so a mutation issued by
agent-viewer and one issued by Codex Desktop converge on the same client state. Note the
asymmetry: `ThreadUnarchiveResponse.json` is 53.5K (returns a full `Thread`) while
`ThreadArchiveResponse.json` is 114B (empty ack).

## 6. Risk: how experimental is this?

`codex app-server --help` opens with `[experimental] Run the app server or related tooling`,
and `generate-json-schema` / `generate-ts` are themselves marked `[experimental]`.

**Versioning is real but shallow.** The generated tree splits into `v1/` (only `initialize`)
and `v2/` (the entire 228-file thread/turn API). So `initialize` is frozen at v1 and
everything agent-viewer would use is v2 — a v3 is the plausible breakage vector, and there is
no negotiated protocol-version field in `InitializeParams` to pin against. The only lever is
`capabilities.experimentalApi`, which is an opt-*in* to more churn, not a stability pin.

**Observed schema drift, today, same version.** The live daemon (0.144.4) emits fields absent
from the schema generated by the same binary (0.144.4). `jq -r '.definitions.Thread.properties|keys[]' v2/ThreadListResponse.json` yields:

```
agentNickname agentRole cliVersion createdAt cwd ephemeral forkedFromId gitInfo id modelProvider name parentThreadId path preview recencyAt sessionId source status threadSource turns updatedAt
```

but the live response contains `"extra":null` and `"historyMode":"legacy"`, and
`jq '.definitions.Thread.properties.historyMode, .definitions.Thread.properties.extra'`
returns `null, null`. (`ThreadExtra` and `ThreadHistoryMode` do exist in the `definitions`
block; they are just not wired onto `Thread`.) Practical consequence: **deserialize
permissively.** Rust structs must not be `deny_unknown_fields`, and every non-`required`
field must be `Option`.

Other concrete risks:
- `Thread.path` is explicitly marked `[UNSTABLE]` in its own description. Do not build the
  rollout-reading path on it without a fallback.
- The WebSocket-over-UDS framing is undocumented in any `--help` and was reverse-engineered
  from strace. It could change without notice, and `codex app-server proxy` being already
  broken against it suggests the transport moved and not all callers were updated.
- No `jsonrpc` version field in the envelope means no standard-protocol anchor either.

**Mitigation shape:** treat app-server as an accelerator behind a capability probe
(`codex app-server daemon version` -> `status == "running"`), keep the SQLite reader as the
fallback backend, and fall back on any handshake or decode failure rather than erroring.

## 7. Contention: is the SPEC.md concern still real?

`SPEC.md:100-103` rejected app-server for v1 partly because "its control socket is already
contended on this box". The evidence for that was
`~/.codex/app-server-control/app-server.log`, which contains exactly one line:

```
Error: app-server control socket is already in use at /home/example/.codex/app-server-control/app-server-control.sock
```

**That line is about binding as a server, not connecting as a client.** The socket has a
single listener:

```
$ lsof ~/.codex/app-server-control/app-server-control.sock
COMMAND   PID       USER   FD   TYPE             DEVICE SIZE/OFF   NODE NAME
codex   23921 example-user   31u  unix 0x0000000000000000      0t0 148814 /home/example/.codex/app-server-control/app-server-control.sock type=STREAM (LISTEN)
```

A second `codex app-server --listen unix://` would fail to bind; that is what the log records.
Clients are unaffected.

**Verified: concurrent clients are fine.** Three simultaneous connections, each with its own
`initialize`, all succeeded, and each issued a different request on its own connection:

```
THREE CONCURRENT CLIENTS CONNECTED AND INITIALIZED OK
loaded/list: {"id":10,"result":{"data":[],"nextCursor":null}}
DEFAULT sourceKinds -> n= 11 ...
ALL sourceKinds -> n= 100 ...
```

That was a fourth, fifth and sixth connection alongside whatever Codex Desktop already holds,
and `codex app-server daemon version` had also just connected and disconnected cleanly. The
daemon is a normal multi-client server.

### Verdict: the contention concern is resolved. It was a misread of a bind error.

The residual concurrency risk is **semantic, not transport-level**: if agent-viewer
`thread/resume`s a thread that Codex Desktop is actively driving, both clients are attached to
the same live thread and `turn/steer` from either goes into the same conversation. That is the
intended design (it is how rejoin works), but it means agent-viewer must not silently resume
threads in the background — resume only on explicit user attach, and `thread/unsubscribe` on
detach.

## 8. What I could not determine

1. **Notification scope for an unsubscribed connection.** Whether a bare
   `initialize`d connection receives `thread/status/changed` for all daemon-hosted threads or
   only for threads it has `resume`/`read`-subscribed. `thread/loaded/list` was empty for the
   whole window, so no transition ever fired. *Speculation: lifecycle notifications are
   global, item/turn deltas are subscription-scoped.* Must be tested against a live turn.

2. **Whether an externally-launched `codex` TUI ever appears as `active`.** No external codex
   session was running during the window (`pgrep -af codex` showed only the daemon), so the
   claim in section 4 that CLI-owned sessions are invisible to the daemon is *inference from
   the "loaded in memory" wording plus a 100/100 `notLoaded` sample*, not a direct observation.
   **This is the single most load-bearing unverified claim in this document** and should be
   settled before any migration decision: start a `codex` session in a terminal, then call
   `thread/loaded/list` and `thread/list`.

3. **Whether `thread/resume` on a daemon-hosted running thread truly avoids duplication.** The
   schema says "rejoins", which I trust, but I did not execute it (write-path constraint).

4. **The exact default `sourceKinds` set.** Observed behavior shows `vscode` in and `exec`
   out; whether `cli` and `appServer` are in the default could not be isolated because no
   `cli`-sourced thread appeared in the sampled page. Pass `sourceKinds` explicitly regardless.

5. **Rename durability.** `thread/name/set` was not executed (write-path constraint), so
   "genuine rename" rests on the three structural signals in section 5, not on a round-trip.

6. **Behavior when the daemon is not running.** `codex app-server daemon version` reported
   `"status":"running"` throughout; I did not (and per constraints could not) test the
   not-running response shape that the fallback logic would key off.

7. **Whether `codex app-server proxy` is intended for a different socket.** Its `--sock` flag
   suggests other sockets exist (`~/.codex/app-server-control/desktop-ssh-websocket-v0.sock`
   is also present). Its failure against the control socket is confirmed; its intended use is
   not.

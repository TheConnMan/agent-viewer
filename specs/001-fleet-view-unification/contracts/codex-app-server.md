# Contract: Codex app-server (metadata plane only)

Transport and the exact call surface agent-viewer depends on. Interaction never goes through
this interface (D-001); it is metadata only.

## Transport

- Discover the socket via `codex app-server daemon version` -> `socketPath`. **Never hardcode.**
- Availability gate is `"status":"running"`. When it is not running, fall back to read-only
  `state_*.sqlite` enumeration. **MUST NOT** start a daemon silently - that is a user-visible
  side effect (D-009).
- Speak **WebSocket** over the Unix socket: HTTP `Upgrade: websocket` handshake, then RFC6455
  text frames carrying JSON-RPC **without** a `jsonrpc` field.
- **MUST NOT** use `codex app-server proxy` - broken in 0.144.4 (literal byte relay, no upgrade).
- Deserialization MUST be permissive. The live 0.144.4 daemon emits `extra` and `historyMode` on
  `Thread` which the schema generated by that same binary does not declare. `Thread.path` is
  marked `[UNSTABLE]` and MUST NOT be used for identity.

## `initialize`

Sent once per connection before any other call.

```json
{"id":1,"method":"initialize","params":{"clientInfo":{"name":"agent-viewer","version":"..."}}}
```

Notifications flow after this with no subscription. `capabilities.optOutNotificationMethods`
mutes the per-token delta firehose and SHOULD be used.

## `thread/list` - enumeration

```json
{"id":N,"method":"thread/list","params":{
  "limit":200, "cursor":null, "archived":false,
  "sourceKinds":["cli","exec"], "useStateDbOnly":true}}
```

Contract requirements:

- `sourceKinds` MUST be passed explicitly. The default drops subagents (desired) **but also
  drops `exec`** (not desired).
- `useStateDbOnly: true` MUST be set. It skips the JSONL repair scan, which is what makes a 1-2s
  refresh viable against 4,194 threads.
- Pagination MUST follow `nextCursor` only. **A short page is not the end of the list** - 11 rows
  were observed for `limit: 200` with a non-null `nextCursor`.

Fields consumed: `id`, `name`, `preview`, `cwd`, `gitInfo.branch`, `gitInfo.originUrl`,
`updatedAt`, `status`, `source`.

## `thread/name/set` - rename

Real rename (D-006). `name` is persisted separately from `preview`. The response is an empty
ack, so success MUST be read as absence-of-error plus the `thread/name/updated` notification -
never as a returned name.

## `ThreadStatus` - the attach gate

```
notLoaded | idle | systemError | active { activeFlags: waitingOnApproval | waitingOnUserInput }
```

- `active.activeFlags` maps natively to needs-input. No inference required.
- `notLoaded` means no daemon-side host. It MUST NOT be mapped to `Done` - a thread launched
  outside the daemon is `notLoaded` while still running, so liveness for those comes from
  `/proc/fd` PID correlation and the rollout tail.
- Attach uses `--remote` for every status (D-004), which converges `notLoaded` threads onto the
  daemon. The **one refusal case** is `notLoaded` **plus** a live external process holding the
  thread: loading it into the daemon then would duplicate it.

## Notifications consumed

| Method | Use |
|---|---|
| `thread/status/changed` | status for daemon-hosted threads only |
| `thread/name/updated` | rename confirmation |
| `turn/started`, `turn/completed` | activity |

**Limit that must be encoded**: the daemon reports status only for threads it hosts. Under D-004
every CLI session is permanently `notLoaded` from the daemon's view, so these notifications do
**not** deliver live status for the sessions agent-viewer primarily watches. Those come from
inotify on the rollout file plus `/proc/fd` correlation (D-007).

## `thread/start` - session creation

Used to create daemon-hosted sessions (D-011). The daemon becomes the session host, so the
session keeps working while detached and survives agent-viewer exiting. Params of interest:
`cwd`, `sandbox`, `approvalPolicy`, `model` config overrides.

Returns `result.thread.id`, which is the identity used for attach and for every later call.

## Attach is NOT an app-server call

Attach spawns the **native TUI pointed at this same daemon** (D-004):

```
codex resume --remote unix://<socketPath> <thread_id>
```

`--remote` is documented as "Connect the TUI to a remote app server endpoint", accepting
`unix://PATH`. This is what keeps the interaction plane native (D-001) while the daemon remains
the host. Verified: `thread/loaded/list` returned exactly one entry while the TUI was attached,
and the thread stayed loaded after the TUI exited.

`--fork` MUST never be passed. `codex fork` is a separate subcommand; `resume` does not fork.

## Explicitly not used

- `thread/resume` from agent-viewer's own client - agent-viewer never becomes the interactive
  client for a thread. The TUI does that via `--remote`. Reading metadata does not require it.
- `turn/steer` - would mean agent-viewer injecting into a live turn, which belongs to the
  interaction plane and therefore to the native TUI.

## Concurrency

Multiple simultaneous clients are safe; three concurrent connections were verified initializing
and serving different requests alongside Codex Desktop's own. The `SPEC.md:100-103` claim that
"the control socket is already contended" is a misread of a **bind** failure from a second
would-be server (D-008). The real risk is semantic, and not calling `thread/resume` forecloses
it.
